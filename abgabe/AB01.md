## 1. DAO-Pattern: create-Methode

> Erläutert das Zusammenspiel von `DaoImp`, `PatientDao` und der Datenbanktabelle `patient`, wenn die im Interface `Dao` definierte Methode `void create(T t) throws SQLException` aufgerufen wird.

Die Methode `create()` wird über das `Dao<T>` Interface aufgerufen, 
`PatientDao.create()` delegiert dabei die Aufgabe an `DaoImp.create()`.
`DaoImp.create()` nutzt dafür die abstrakten Methoden `getCreateStatement()` und `getCreateStatementMapping()`, 
die von `PatientDao` konkret implementiert werden.
`DaoImp` ist eine abstrakte Implementation der Data-Access-Objekt Architektur, 
welche die CRUD (Create, Read, Update, Delete) Struktur darstellt.
Sie dient dafür, die Kommunikation zwischen dem Java Programm und einer Datenbank zu definieren, 
ohne das der aufrufende Code selbst Datenbankcode benötigt.
`PatientDao` ist die Implementation dieser Klasse zur Kommunikation mit der `patient` Tabelle.
Die fertige SQL-Insert-Anweisung wird dann über `ConnectionBuilder.getConnection()` ausgeführt und 
der neue Eintrag in der Datenbank gespeichert.

## 2. Erweiterung um ein Pfleger-Modul

> Was müsstet ihr tun, um ein Modul zur Verwaltung von Pflegekräften zu ergänzen? Welchen Vorteil bietet die Architektur mit generischem `DaoImp<T>` gegenüber einer Architektur mit konkreten DAO-Klassen pro Model?


Für die Implementation werden die folgenden Elemente benötigt:

- Eine `Caregiver`-Klasse als Model, die von `Person` erbt (analog zu `Patient`)
- Eine Erweiterung der SQL Datenbank um eine `caregiver`-Tabelle
- Eine Implementation von `DaoImp` namens `CaregiverDao`
- Ein neues FXML-File welches die Pfleger darstellt und bearbeiten lässt
- Ein neuer Knopf in `MainWindowView` welches das neue Panel im Center öffnet
- Die `DaoFactory` muss um einer Factory Methode für `CaregiverDao` erweitert werden.

Der Vorteil von der generischen `DaoImp` Klasse ist es, 
dass die Basisfunktionen die für jede Datenbankveränderung benötigt werden, 
immer implementiert werden müssen und dass die Schnittstellen in allen Datenbankklassen gleich sind. 
Neue Entitäten müssen so nur die spezifischen SQL-Statements implementieren, nicht die gesamte Datenbanklogik.

## 3. ConnectionBuilder, DaoFactory und das Singleton-Pattern

> Erklärt die Aufgaben der Klassen `ConnectionBuilder` und `DaoFactory`. Warum hält `PatientDao` keine eigene Datenbankverbindung? Warum sind beide Klassen Singletons?

Die `DaoFactory` verwaltet die Erstellung von Data-Access-Object Klassen.
Die `ConnectionBuilder` Klasse verwaltet die Verbindung zu der Datenbank.

Beide Klassen nutzen das Singleton Pattern, wodurch nur eine Instanz von deren Klassen geladen werden.

Dies ist nützlich, weil das konstante Erstellen dieser Klassen unnötige Verluste bei der Geschwindigkeit des Programmes verursachen würde. 
Für den `ConnectionBuilder` hat es auch den Vorteil, dass das Verwalten der externen Verbindung zur Datenbank zentralisiert ist. 
Das Öffnen und Schließen passiert an einem einzigen Ort.

`PatientDao` hält keine eigene Verbindung, weil `DaoImp` bei jedem Aufruf `ConnectionBuilder.getConnection()` nutzt. 
Würden einzelne DAO-Klassen diese Verbindungen selbst verwalten, 
könnte es leicht zu Fehlern kommen und Verbindungen würden möglicherweise nicht richtig geschlossen werden.

## 4. MVP-Pattern

> Erklärt das Zusammenspiel von `Patient`, `AllPatientController` und `AllPatientView.fxml`, wenn ein Benutzer einen neuen Patienten anlegt und auf *Hinzufügen* klickt. Worin liegt der Unterschied zu MVC?

Diese Komponenten sind so aufgeteilt:

- **View:** `AllPatientView.fxml`
- **Model:** `Patient`
- **Presenter:** `AllPatientController`

Der Unterschied zu der MVC Architektur liegt darin, dass View und Model komplett getrennt sind.
In dem MVC Pattern bekommt die View die Model Daten direkt, 
in dem MVP Pattern bekommt die View ihre Daten von dem Presenter, 
welcher als Mittler zwischen der View und dem Model agiert.

Der Knopfdruck zum Erstellen eines Patienten löst die Methode `handleAdd()` im `AllPatientController` aus, 
welche die Eingaben aus den TextFields der View ausliest. 
Der Presenter erstellt ein neues `Patient`-Objekt und ruft `dao.create(patient)` auf. 
Daraufhin aktualisiert der Presenter die TableView, um den neuen Patienten anzuzeigen.


## 5. Erste eigene Änderung

> Welchen Weg nehmen die Daten vom `SetUpDB`-Aufruf bis zur Anzeige in der GUI?

Wir haben in SetUpDB diesen neuen Eintrag in der "setUpPatients" Methode hinzugefügt:
```java
    dao.create(new Patient("Henrik", "B", convertStringToLocalDate("2006-06-12"), "1", "112", "arm"));
```

Die setUpPatients methode wird von der setUpDb Methode ausgeführt. 
Der Ablauf der setUpDb Methode ist isoliert von dem Rest des Programmes. Sie wird nur ausgeführt, 
wenn die main() methode von SetUpDB.java ausgeführt wird. 
Das bedeutet, dass der Eintrag nur durch die Ausführung der main() methode in der Datenbank erscheint.

Die Daten werden trotzdessen in der GUI angezeigt, weil die setUpPatients methode ihre änderung in der Datenbank sichert, welche
von dem Hauptprogramm verwendet wird, um die Daten anzuzeigen.
